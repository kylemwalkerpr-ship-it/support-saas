## S6 source security review of 014–018

This is a source assessment in the S6 engineering attempt, not independent organizational approval or a native execution attestation.

* **Privileges and ownership:** 014/015 initially grant service RPC access; 016 renames/revokes internal functions and introduces membership-guarded wrappers. 017 exposes only DENY coordination/retry bookkeeping. 018 creates no role, endpoint, enrollment or runtime flag, and revokes candidate/suppression function and table access from PUBLIC, anon, authenticated and service_role. Its final ACL checks reject inherited runtime privileges. RLS is enabled without browser policies. BYPASSRLS alone supplies no table privilege. The privileged function owner bypasses RLS by design and must never be a runtime identity. Preserve the exact 018 denial; no positive role/grant was added outside the disposable harness.
* **SECURITY DEFINER:** functions pin `search_path=pg_catalog,public`; authority tables are schema-qualified. Before any future authorized migration, independently inspect function owners, schema CREATE ACLs, extensions and inherited/default privileges. `public` must not be writable by untrusted principals. Pinning search_path is not permission to trust a writable public schema. Do not expose the intermediate 014/015 wrappers during a staged rollout.
* **Current authority:** literal support/portal/tenant rows are locked and current active membership, enabled issuance, consent epochs, disclosures and exact scopes are checked. These literals are synthetic, not real provisioning. Support membership contains no Clerk issuer/party provenance; portal deployment has issuer/party but 018 does not compare them with a verified session/proof issuer. The candidate JSON contains no authenticated issuer. Those remain trusted-adapter and provisioning gaps, not SQL-proven properties. A matching shared Supabase URL proves neither live schema/grants nor that authority exists.
* **Challenge/session:** SQL binds the challenge to portal subject, site, tenant, support site, epoch, version, scopes, purpose, pending state, expiry and supplied session digest. Unique challenge binding prevents a second ledger consumption. It does not compute that digest from a real immutable sid, verify a cookie, or detect logout. Session expirations and all proof/request digests are supplied assertions. No authenticated positive adapter bridges the JS inspector to SQL. A valid-looking digest or expiration is not authority.
* **Replay and mutation:** exact request bindings must match a still-committed pair for retry. Request, pair+epochs, each proof digest column and challenge are unique; the replay table makes both sites' JTIs globally unique across columns. Digest uniqueness is per proof column, not a cross-column digest registry. Digest bytes are not recomputed by SQL. There is no cryptographic validation in 018. Typed authenticated original-byte validation and durable retention are required before considering a new positive design.
* **Locking and expiry:** candidate order is support deployment SHARE, portal deployment SHARE, support member SHARE, portal member SHARE, support consent UPDATE, portal consent UPDATE, challenge UPDATE, ledger advisory fence, prior ledger and replay inserts. The database clock is read after all blocking locks, including the fence. Proof expiry is capped at 120 seconds and bounded by challenge expiry; both asserted session expirations must be future. Membership/deployment UPDATEs conflict with SHARE. Triggers take authority row then the same ledger fence and atomically revoke old-identity pairs with a pending outbox event. Grants also suppress; they never revive a pair. Concurrent administrative transactions can deadlock if they acquire authority rows in reverse order; retry the whole aborted transaction and never treat a partial result as permission.
* **Withdrawal and S4:** 016 permits retained suspended/revoked members to withdraw even when issuance is off; unknown membership denies and requires an approved recovery process. 014 appends the epoch tombstone and 017 enqueues suppression in the same transaction. 018 revokes matching pairs and records one pending event per pair in that transaction. Failure rolls back all effects. Pending is not signed delivery or an ACK. No cleanup, sender or acknowledged propagation is implemented. Retain both S4 and candidate outboxes plus all JTIs and tombstones beyond proof/retry/restore horizons.
* **Restore:** uniqueness and CAS cannot protect against restoring an older database that lost withdrawals. No restore reconciliation/online session revocation authority is implemented. Restores must remain fenced from issuance and derived use until independently reconciled with durable withdrawal/replay high-water evidence. Do not restore an old grant over a newer withdrawal, delete a tombstone, reuse synthetic reset logic, or roll back to permissive internal RPC grants.
