## Implementation boundary

`lib/privacy/live-authority.mjs` exports a production-shaped verifier engine, not a wired endpoint. Existing runtime `signing.enabled=false`, account `redeem` denial, reciprocal denial, visitor X-Chat-Token handling, sender privacy and SQL 018 ACLs are unchanged. No migration or grant is added. There is no environment toggle that activates this module.

`createOnlineSessionVerifier` combines SDK signature verification with a fixed `https://api.clerk.com/v1/sessions/{verified_sid}` backend request. It requires a pinned issuer, literal HTTPS party, local JWT key, separately provisioned backend credential, exact immutable subject/session, exp/iat/nbf and current active backend session with matching id/user and expiration. No discovery, redirects, URL-supplied authority or positive cache. Fetch has a five-second timeout; errors deny. This helper is not installed into existing review/withdrawal runtime, whose availability and behavior remain unchanged. Tests inject transports; no Clerk request was performed. Actual Clerk token shape, timeout behavior and credential-to-instance provenance require independent deployment acceptance.

`authorizeLiveLink` snapshots bounded original compact proofs, opaque credentials and challenge. It authenticates a third, separate ES256 service identity with 30-second maximum envelope lifetime, exact scope `q02:link`, tenant, request digest, JTI, issuer and coordinator audience. The digest is SHA256/base64url of UTF-8 JSON array `[supportProof, receipt, challenge, SHA256(supportCredential), SHA256(portalCredential)]`. Neither opaque credential is persisted by the engine. The strict envelope header is `{alg:'ES256',typ:'q02-service+jwt',kid}`; payload is exactly `{v:1,iss,aud,sub,scope,tenant,request_digest,jti,iat,nbf,exp}`. JSON must roundtrip exactly; unknown fields, untrusted keys and noncanonical base64url deny. No browser service signing helper is exposed.

It reuses the existing strict independent support/portal proof inspectors: exact original-JWS digests, reciprocal support JTI, challenge, both immutable subjects, current versions and scopes, bounded key manifests, mathematical key separation and separate online session verifiers. Service keys must also be mathematically separate from all site proof keys. Issuer identity and key validity/revocation are selected from locked server authority, not request data. The preserved candidate namespace is literal `support`, `portal`, `tenant`; it is not evidence of production ownership.

Explicit locked rows must match each verified session's issuer, party, immutable sub/sid, independently managed active membership and credential enrollment, active consent epoch, exact disclosure and scopes. The challenge must match portal owner, verified session digest, epoch, pending state and lifetime. A locked post-verification `assertCurrent` is additionally required. Missing reconciliation generation/high-water, lagging local or portal watermarks, pending outbox or absent ACK denies. A successful `consume` must report atomic commit intent, same request digest, durable event digest and both durable ACKs. Replay IDs span support, portal, service and challenge. The outer adapter must actually commit before returning. Result `LINKED` is only a link receipt, with `derivedUse:false`; no derived read wrapper exists.

The positive integration uses a transactional synthetic port and ephemeral signatures, not PostgreSQL or real service credentials. It proves protocol/verifier behavior, not that a deployed database implements that port. The stale/revoked/missing-enrollment cases mutate explicit locked row fixtures. Production durability, concurrent revocation serialization, withdrawal delivery and restore reconciliation remain unmet. A caller-supplied or browser-built adapter is never an authority.

## Portal V8 and coordinator implementation contract (unmet)

A separately fenced portal worker must implement this exact protocol and tests before any support route can call the engine. V7 alone cannot satisfy it. Keep V7 `portal-v7-1` reciprocal wire payload and support `q02-support-v1` byte contract; a disclosure change requires coordinated version updates and fresh opt-in, never silently reinterpret existing consent.

1. Portal browser POST remains same-origin, authenticated `__session`, exact JSON and no proof/credential in URLs, storage, telemetry or logs. Verify the pinned portal issuer/party/session online. Resolve independently managed tenant+immutable-sub membership and explicit credential enrollment; never enroll from email, profile joins, shared Clerk users, request bodies or webhook claims alone. Preserve review/withdraw when issuance disabled or membership suspended. Anonymous and support-only sessions deny portal issuance.
2. Portal reserves a 256-bit challenge with current consent epoch/version/scopes and SHA256/base64url of verified sid, under its existing deployment/member/consent lock order. Independently sign the V7 ES256 reciprocal receipt over exact support proof bytes and JTI. Receipt expiration is bounded by support proof, challenge and both verified sessions. No receipt itself authorizes consumption.
3. Server-to-coordinator POST `/internal/q02/v8/link` carries exactly the engine input fields. This is a proposed new internal API, absent in both sources today. A separately enrolled service signs the service envelope, plus authenticated workload transport (mTLS or fixed Cloudflare service binding). Never expose this API via public browser RPC or use anon, authenticated, generic service_role, staff role or user bearer token as the service principal. Public proofs alone cannot call it. Different tenants/principals need separate scoped enrollment. Disallow redirects and arbitrary coordinator destinations.
4. Implement `protocol:'q02-locked-authority-v8'` and `withLockedAuthority(requestDigest, callback)` in a dedicated coordinator process owning a single actual PostgreSQL transaction. It must load all dependencies after locks, hold locks through both online calls, callback and DB-clock recheck, and COMMIT before resolving. Abort/timeout/disconnect/ambiguous commit => DENY, followed by read-only reconciliation; never retry with a new JTI to evade uncertainty. No sequence of Supabase HTTP RPC calls satisfies this transaction contract. No existing service-role RPC is sufficient. Lock acquisition is bounded; online calls must not prolong transactions indefinitely.
5. Locks: existing SQL 018 fixed deployment support/portal -> membership support/portal -> consents support/portal -> portal challenge -> replay advisory fence -> ledger ordering must remain. Add separately reviewed service/key/enrollment/restore fences in a single global ordering observed by their administrative revocation paths too. `tx.service`, `tx.authorities`, `tx.current`, `tx.outbox`, `tx.reconciliation` are fresh locked rows, not environment assertions. `tx.current.support/portal` fields are site, tenant, subject, issuer, party, membership, enrolledSid, credentialStatus, issuance, state, epoch, version, scopes. Challenge fields are value, subject, sessionDigest, state, epoch, expiresAt. Only hashes of sid are durable where feasible. `assertCurrent(binding)` rechecks DB wall clock, key/service status, both sessions and enrollment under locks. A remote Clerk logout cannot be made atomic with PostgreSQL: the online request is a point-in-time assertion. Live acceptance must define this residual race and require fresh online checks at every use; never claim globally atomic Clerk logout.
6. `consume(binding)` atomically rejects already-used support/portal/service JTIs or challenge across all columns, inserts immutable exact binding and link event, checks both durable signed ACKs for that binding, and returns exactly `{committed:true, requestDigest, eventDigest, bothAcknowledged:true}`. No idempotent successful replay. A previously committed request can be reviewed separately but is never a new authorization. Do not hold a DB transaction open while waiting on remote ACK delivery. Stage a pending link event first, deliver and obtain ACKs outside the final transaction, then perform fresh locked online authorization and final consumption against the same immutable binding within proof expiry. Expired staging stays suppressed. This staging/durable event API is not implemented in S8; the synthetic adapter assumes reconciled ACKs. No partial two-site link can become usable.
7. Withdrawal, membership/credential/service revocation and challenge cancellation first suppress locally under the same locks, invalidate pending/committed link state and atomically append durable outbox events. Events contain protocol version, fixed issuer/audience, event JTI/digest, pair digest, both sites, tenant, immutable subjects, cause, strictly monotonic source sequence, consent epochs, generation and issued time; sign using separate enrolled event keys. Proposed internal POST `/internal/q02/v8/events` accepts only fixed peer service and pinned key. Receiver locks high-water and pair, validates signature/bindings/monotonic sequence, persists tombstone/suppression and exact received digest, then commits before signing ACK. ACK binds original event digest, pair, receiver, audience, generation and applied high-water. Duplicate exact events may return the same durable ACK; mismatched duplicates or gaps deny and suppress. Sender verifies ACK signature and fixed identity, then durably records it. Delivery retries are bounded/backed off, crash-safe and idempotent; no logs of proofs or credentials. Missing ACK, delivery outage or sequence gap denies both sites' derived use. SQL 018's pending-only outbox is insufficient and must not be treated as delivered. S8 implements no dispatcher, signing worker or ACK persistence.
8. Restore: issuance and use off before rollback/restore. Preserve append-only replay/tombstone/outbox history beyond proof+retry+backup horizons. Compare both peer watermarks with an independently retained append-only high-water checkpoint; restoring both databases must not restore the checkpoint backwards. Reconcile all missing events and ACKs, verify digests, rotate generation and revoke pending credentials/proofs before marking ready. `ready`, `generation`, `highWater`, `local`, `portal` cannot be operator booleans with no evidence. Missing checkpoint or unrecoverable gap => permanently deny affected generation; fresh enrollment/consent cannot erase suppression. No restore-ready implementation exists here.
