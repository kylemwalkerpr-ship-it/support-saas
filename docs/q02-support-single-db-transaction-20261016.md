## Atomicity and fencing contract

Lock order is fixed: support deployment SHARE → portal deployment SHARE → support membership SHARE → portal membership SHARE → support consent UPDATE → portal consent UPDATE → portal challenge UPDATE → advisory ledger/replay fence `(180216,1)` → existing ledger UPDATE → inserts into ledger/replay registry. Missing rows deny. The advisory fence serializes absent ledger rows and all unique-index CAS waits **before** the DB clock check. Expiry is rechecked with `clock_timestamp()` after acquiring all locks, including idempotent replay: challenge, proof and both asserted session lifetimes must still hold. Proof lifetime is capped at 120 seconds. Portal challenge binds exact subject/site/tenant/support site, epoch/version/scopes/purpose and independently verified session digest.

One transaction inserts the pair ledger, both globally unique replay IDs and unique challenge/digests. The unique ledger challenge is the consumption CAS; V7's pending/cancelled challenge wire contract is preserved. Pair+both epochs are unique. Exact current retries return RECORDED/replayed with derivedUse false; changed bindings, stale/revoked pairs, alternate requests for the same pair and any cross-site JTI reuse fail transactionally. RECORDED is a synthetic ledger receipt, never an authorization capability. SQL exceptions, connection termination and rollback must erase every uncommitted CAS effect. A caller must retry the whole transaction after deadlock/serialization failure; never reuse a prior result as permission.

Additive AFTER UPDATE/DELETE triggers on both consent, membership and deployment tables and portal challenges take the same ledger fence. They revoke only pairs bound to the changed OLD immutable identity or exact challenge; deployment changes revoke the entire matching fixed namespace. Any consent change conservatively suppresses, including regrant. Withdrawal through existing RPC changes its epoch, preserves predecessor tombstones/outbox, marks bound candidate pairs revoked and inserts one pending event per pair **in the same transaction**. Event includes exact old/new authority record, source table/operation and a SHA256 digest over pair plus canonical JSONB event. Membership suspension/revocation, deployment/tenant reassignment and challenge cancellation cannot leave a bound candidate usable. Rows, subjects, replay IDs and lawful commercial/source records are retained. No ACK function, sender or retry loop exists, hence no false delivery success or retry storm. S4's bounded retry bookkeeping is unchanged.

Managed registry administration must retain immutable rows and follow deployment → membership → consent ordering. A trigger is a final fence, not permission to perform arbitrary multi-row administrative transactions in conflicting order. Withdrawal locks its own authority then ledger and never acquires another site's authority. Potential deadlocks abort safely and require full-transaction retry. Future derived effects must acquire the **same complete authority locks**, recheck DB clock, memberships, both epochs and pair state, and atomically commit their actual effect under those locks. A standalone boolean authorization read is forbidden. Pending/unknown propagation or restore state must deny. This prototype exposes no derived-use function at all.

No claim is made that logout is persisted to this shared DB: an asserted session expiry alone cannot prove non-revocation. Likewise restored backups can restore old epochs/replay data. Both are remaining authority gates; no runtime role can use the prototype to bypass them.
